# Описание проекта Tile Downloader

## Обзор проекта

Tile Downloader — приложение на Python для систематического скачивания тайлов
спутниковых карт с Яндекс Карт и их хранения в автономной мастер-БД SQLite.
Проект выполнен в **клиент-серверной** архитектуре: один сервер владеет
мастер-БД и координирует работу, а множество клиентов (процессов/машин)
параллельно докачивают тайлы. Это устраняет дублирование загрузок и делает
процесс устойчивым к падениям клиентов и сервера.

## Ключевые свойства

- **Единый источник истины** — мастер-БД сервера; клиенты лишь транспортируют тайлы.
- **Никакой тайл не выдаётся двум клиентам одновременно** — выдача под блокировкой
  с учётом in-flight диапазонов.
- **Идемпотентная запись** — `INSERT OR IGNORE` по PK `(x, y)`: повторные сабмиты
  и гонки не портят данные.
- **Локальный буфер клиента** — его SQLite-база, переживающая падение клиента
  между «скачал» и «отдал»; остатки досдаются при следующем старте.
- **Докачка старых данных** — сервер сам находит пропуски в существующих
  `tiles_N.db3`; `settings.pickle` больше не нужен.

## Архитектура

```
        ┌──────────────────────────────────────────────┐
        │            SERVER (server.py)                │
 клиенты ──HTTP──▶  GET /api/task                    │
 (client.py)        POST /api/tasks/{id}/submit        │
 на разных          POST /api/tasks/{id}/heartbeat      │
 машинах            GET /api/status /api/events         │
                    GET /dashboard                      │
                    jobs.py (ядро, без сети)            │
                    tiles_N.db3 + jobs.db3             │
        └──────────────────────────────────────────────┘
        КАЖДЫЙ КЛИЕНТ:
        buffer_<client_id>.db3  (локальный буфер)
          1. GET /api/task  ->  {zoom, start_idx, end_idx}
          2. скачивание диапазона (N потоков, ретраи) -> буфер
          3. POST submit (бинарный фрейм) -> очистка буфера -> цикл
```

### Компоненты

- **server.py** — HTTP-сервер на aiohttp: маршруты API, дашборд, фоновый
  TTL-рипер (`reap_expired`).
- **jobs.py** — ядро без сети: выдача задач (диапазонов индексов), учёт
  in-flight, приём тайлов, возврат в пул, TTL/heartbeat, выбор зума, статистика.
- **client.py** — клиент-рабочий: `ServerAPI` (aiohttp), `download_range`
  (Semaphore-параллельность, ретраи), главный цикл `run` (досдача остатков,
  фоновый heartbeat), `main`.
- **buffer.py** — локальный SQLite-буфер клиента (`ClientBuffer`).
- **db.py** — доступ к мастер-БД (`Repository`: per-instance соединение/буфер/лок,
  `INSERT OR IGNORE`, рядовые fast-path проверки).
- **protocol.py** — бинарный формат фрейма сабмита (`encode_submit`/`decode_submit`).
- **dashboard.py** — HTML-дашборд (инлайн-стили/JS, читает JSON-эндпоинты).
- **utils.py** — `get_xy` (линейный индекс ↔ координаты) и форматирование.
- **reduce.py** — поиск дублей в мастер-БД.

### Технологический стек

- Python 3.8+, asyncio + aiohttp
- SQLite (WAL) — мастер-БД, `jobs.db3`, буферы клиентов
- Бинарный протокол сабмита (не JSON) — экономия ~30 % трафика и CPU

## Протокол HTTP

Все ответы — JSON `{"ok": true, ...}` либо `{"ok": false, "error": ...}`
с кодом 400/404/413.

| Метод и путь | Описание |
|---|---|
| `GET /healthz` | Сервер жив |
| `GET /api/task?client_id=` | Выдать задачу или `{"task": null, "done": bool}` |
| `POST /api/tasks/{id}/submit?client_id=` | Сдать тайлы (бинарный фрейм) |
| `POST /api/tasks/{id}/heartbeat?client_id=` | Продлить deadline задачи |
| `GET /api/status?window=300` | Статистика: слои, клиенты, скорость |
| `GET /api/events?limit=50` | Журнал событий аудита |
| `GET /dashboard` | HTML-дашборд |

Тело задачи: `{"task": {"task_id", "zoom", "start_idx", "end_idx", "count", "deadline"}}`.

## Модель данных

- Тайл — тройка `(zoom, x, y)`, `x, y ∈ [0, 2^zoom)`. Линейный индекс
  `idx = y·2^z + x` (строка-мажор).
- Мастер-БД: `tiles_{zoom}.db3`, таблица `z{zoom} (x, y, image, ext)`,
  PK `(x, y)`, индекс по `y`, WAL.
- `jobs.db3`: `meta` (курсор/счётчики), `tasks` (журнал задач), `events` (аудит),
  `submits` (источник скорости приёма).
- Буфер клиента: `buffer_{client_id}.db3` (таблицы `buffer`, `buffer_meta`).

## Жизненный цикл задачи

```
     issue()               submit()              reap()
free ──▶ issued ───────────▶ submitted (в мастер-БД)
           │  ▲                    │
           │  │ остаток диапазона  │ (не присланные тайлы)
           │  └──────────────────▶ free
           ├─ deadline (TTL-рипер) ─▶ reaped ─▶ free
           └─ клиент запросил новую задачу ─▶ reaped ─▶ free
```

Задача — крупная (десятки минут работы). Heartbeat редкий и идёт фоновым
потоком на всё время задачи, включая фазу передачи результата, поэтому сервер
не «убивает» задачу живого клиента во время долгого сабмита. «Молчаливо» умерший
клиент освобождается не позднее `task-ttl + heartbeat-interval` (~20 мин по
умолчанию).

## Параметры конфигурации

### Сервер (`python server.py --help`)

- `-o, --output-dir` — каталог мастер-БД и `jobs.db3` (по умолчанию `.`)
- `--host` / `--port` — адрес и порт (по умолчанию `0.0.0.0` / `31059`)
- `--min-zoom` / `--max-zoom` — диапазон зумов (по умолчанию `1` / `14`)
- `-z, --zoom` — только зум N
- `--chunk-size` — размер задачи в тайлах (по умолчанию `2000`)
- `--task-ttl` — время жизни задачи без heartbeat, c (по умолчанию `900`)
- `--reap-interval` — период TTL-рипера, c (по умолчанию `15`)

### Клиент (`python client.py --help`)

- `--server` — URL сервера (по умолчанию `http://127.0.0.1:31059`)
- `--client-id` — идентификатор клиента (по умолчанию имя хоста)
- `--buffer-dir` — каталог локального буфера (по умолчанию `./buffer`)
- `--threads` — потоков на скачивание (по умолчанию `16`)
- `--tile-url` — шаблон URL тайла (по умолчанию Яндекс Карт)
- `--heartbeat-interval` — период heartbeat, c; `0` — выключить (по умолчанию `300`)
- `--retry-delay` — пауза между ретраями, c (по умолчанию `30`)
- `--once` — одна задача и выход

## Обработка ошибок и отказоустойчивость

- Сетевые сбои источника — ретраи с паузой (`--retry-delay`); неисцелимые сбои
  возвращают тайл в пул через «остаток диапазона» и он будет выдан повторно.
- Падение клиента — скачанное сохранено в локальном буфере и досдаётся при старте.
- «Молчаливая» гибель клиента — освобождение по TTL-риперу.
- Рестарт сервера — все `issued` задачи переводятся в `reaped`, счётчики
  пересчитываются по мастер-БД; повторная выдача безопасна (идемпотентность).

## Сценарии использования

- Создание автономных карт для регионов с ограниченным подключением.
- Архивирование спутниковых снимков.
- Создание пользовательских репозиториев тайлов.
- Параллельная докачка одной базы множеством машин без дублирования загрузок.
